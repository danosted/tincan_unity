# Test range: controlled scenes for scenario runs

## Context

Scenarios (`.docs/NETWORK_TEST_HARNESS.md`) run in whatever scene is open, which today is the POC scene
`Assets/Scenes/drm_cloud_environment.unity`. That scene was built for playtesting, not for tests:

- **The whole feature set loads.** `Profile_FuelSandbox` pulls in every installer, and each spawns its stations.
- **The pirate-ship prefab is heavy and cluttered.** It has 46 renderers and 48 colliders (ropes, sails, masts,
  stairs, flags), plus legacy test objects (`BoosterTEST`, the old `ShipRepairPoint` and `ShipDamagePoint`). Rays
  can hit rigging, and a teleport can land on stairs.
- **The environment costs time and adds noise.** Volumetric clouds and the atmosphere director add start-up time
  and have already caused false failures (the dirty-scene trap in `CODE_MAP.md`).

Goal: every scenario runs in a small, deterministic world that contains only its feature area, and any contributor (human or agent) can add a feature check the same way.

Decisions taken with the developer:
- **A bare test ship.** An airship with no art: the same network, platform and GAS components, and a flat deck.
- **A scene per feature area, not per scenario.** Every area scene is generated from one builder, so they share a set-up (the plan first said a rig prefab;
  see the log). The feature profile is a field on the scene's lifetime scope, so no core file needs a hook.
- **Installers spawn their own stations,** as in the game. The area's profile decides which ones exist, and
  scenarios only move the subject.
- **Claude and Copilot packaging.** The canonical text lives in `.docs`. Thin `.claude/skills` and
  `.github/prompts` point to it.

## Design

### Test ship: `Assets/Prefabs/Test/TestShip_Prefab.prefab`
- A **prefab variant** of `Airship_Prefab`, so its components stay in sync with the real ship. It removes `Mesh`,
  `BoosterTEST`, `ShipRepairPoint`, `ShipDamagePoint` and `Control_Station`.
- A flat box deck whose top is at **ship-local y = -3.49**, the real deck height. Every authored ship-local pose
  (fixtures, damage sockets) still lands on a deck. A low railing around the edge.

### Area scenes: `Assets/Scenes/Test/`, generated by `DevTools/Editor/TestRangeSceneBuilder.cs`
- Root objects in each scene:
  - a `GameLifetimeScope` instance, with `_airshipPrefab` set to the test ship and the area's `_featureProfile`
    (`GameLifetimeScope.prefab` itself is not edited);
  - `NetworkService`, a sun and a fall-catcher plane;
  - the cloud view with its legacy visuals off (the scope resolves it from the scene).
- No clouds, atmosphere or cloud visuals.
- **TinCan > Dev > Test Range > Rebuild Scenes** regenerates them from the builder's `Areas` table.

| Scene | Profile (`Assets/Settings/FeatureProfiles/Test/`) | Scenarios |
|---|---|---|
| `Test_Core` | `Profile_Test_Core`: Ui, CloudSubmersion, NetTestHarness, GameplayTags, Items, Targeting, Interaction, TestRange | TagRequest, EquipCycle |
| `Test_ShipDamage` | `Profile_Test_ShipDamage`: Core + Fuel + ShipDamage | ShipDamage, RepairLoop, AimPitch, InteractRack |
| `Test_NetCatch` | `Profile_Test_NetCatch`: Core + Fuel + FlyingCan | NetCatch |

- The scenes are in the build list, because clients load the host's scene through NGO scene management.

### Running
- `ScenarioEntry.Scene` names the scene (a path). `null` means "the open scene", for a deliberate playtest-style
  check in the POC scene.
- The scenario menu opens the scenario's scene before Play. It remembers the scene that was open (`SessionState`)
  and reopens it when Play ends.
- `verify.ps1` asks the catalog for the scene, opens it in the main Editor, then syncs the clones to it (the
  existing `Sync-CloneScenes`) before a host + client run. The tier line shows the scene.
- An EditMode test checks that every catalog scene exists and is in the build list.

### Docs and skills
- `.docs/NETWORK_TEST_HARNESS.md`:
  - A new section, "Test range": the ship, the builder, area scenes and profiles, and how to add an area.
  - An updated "Adding a scenario": pick or create the area scene.
  - A troubleshooting table of the failures seen so far.
- `.docs/TUTORIAL_NEW_FEATURE.md` and `.docs/TASK_GUIDES.md`: a slice is done when its scenario passes
  `verify.ps1` in its area scene.
- `AGENTS.md`: one line pointing to the loop.
- `.claude/skills/verify-feature` and `.claude/skills/add-scenario`, plus `.github/prompts/verify-feature.prompt.md`
  and `add-scenario.prompt.md`: short procedures that point to the docs.
- `CODE_MAP.md`: rows for the test range, and a trap about a station that is missing because its installer is not
  in the area profile.
